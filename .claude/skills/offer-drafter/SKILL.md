# Offer Drafter — драфты Soft Commercial Offer для покупателей

Этот skill берёт готовый маркетинговый лист (`output/buyers.xlsx`, собранный skill'ом
`buyer-finder`) и превращает отобранных покупателей в черновики писем в Gmail —
персонализированные Soft Commercial Offer с правильной нумерацией КП, фиксированной
подписью и согласованными вложениями. **В v1 письма только создаются как драфты и НЕ
отправляются** — отправка (сейчас вручную пользователем, в будущем автоматически) это
осознанно следующий шаг за рамками этого skill.

Для создания/чтения драфтов используй Gmail MCP-инструменты (`mcp__...create_draft`,
`get_draft`, `delete_draft` и т.п.) — не пытайся собирать .eml файлы руками или писать
через SMTP.

## Шаг 0. Обязательно: прочитай текущие правила

Открой и прочитай **целиком** `.claude/skills/offer-drafter/rules.md` перед тем как
делать что-либо дальше. Это живой документ — пользователь может добавлять и менять
правила там без предупреждения в чате. Если что-то в этом SKILL.md противоречит
rules.md — **rules.md главнее**, всегда.

Коротко (детали — в rules.md): фиксированная подпись (Fadei Migalcian, FITO VITA SRL),
всё — soft commercial offer, номер КП формата `PRODUCT/yymm-dd_WAVE` на 14 дней, без
конкретных дат в тексте письма, только согласованные вложения, строго последовательное
создание драфтов в обратном порядке относительно таблицы. При ошибке на одной компании —
удалить "бракованный" драфт; реакция на остальную волну зависит от режима (правило 6):
в автономном полном пайплайне — пропустить компанию и продолжить волну, в обычном ручном
запуске — остановить всю волну (как раньше). Подтверждение волны пользователем перед
созданием драфтов (шаг 1) нужно только в обычном ручном запуске — в автономном полном
пайплайне (правило 11) оно пропускается.

## Шаг 1. Определить продукт и волну

1. Уточни (если не очевидно из разговора), под какой продукт готовим эту волну — сверяйся
   с полем `Продукт` в `output/buyers.xlsx` (лист Buyers).
2. Прочитай лист Buyers и отфильтруй компании этого продукта со статусом
   "Не контактировали" (если пользователь явно не попросил другой статус/подмножество —
   например повторную волну для кого-то конкретного).
3. **Обычный ручной запуск** (пользователь сам в чате попросил сделать драфты для
   конкретного списка, не через автономный пайплайн): покажи получившийся список **в том
   порядке, как строки идут в таблице** (сверху вниз), с номером строки для каждой, и явно
   спроси подтверждение волны. Не начинай ничего создавать, пока не получишь однозначное
   "да"/подтверждение. Если пользователь просит убрать/добавить компании — скорректируй
   список и покажи заново.
   **Автономный полный пайплайн** (запущен через `market-supervisor` Шаг 6 из досье по
   продукту — правило 11 `rules.md`): пропусти ожидание подтверждения, переходи к шагу 2
   сразу с этим списком; полный список компаний появится в финальном отчёте Шага 5.

## Шаг 2. Проверить вложения продукта

По умолчанию (решение пользователя от 22.10.2026, rules.md §5) **файловые вложения к
первому письму волны не требуются** — КП это текст самого письма. Этот шаг нужен только
чтобы знать, что реально предлагается, и подготовить 1-2 фразы с перечислением документов,
которые трейдер может выслать позже по запросу покупателя (упоминать это в письме не нужно,
просто держать в голове контекст продукта).

1. Проверь `attachments/<PRODUCT>/manifest.json` (смотри формат в `attachments/README.md`).
2. Если файла нет, он пуст, или `confirmed_by_user` не `true` — **остановись** и спроси
   пользователя, какие документы вообще существуют по этому продукту (даже если они не
   будут вложены файлом в первое письмо — это справочный список для возможного запроса
   покупателя позже). После ответа сохрани список в manifest с `confirmed_by_user: true`,
   `confirmed_date` — сегодняшней датой. Разовая настройка на продукт.
3. Не нужно читать и прикреплять файлы к драфтам этой волны, если пользователь явно не
   попросил вложить документы именно в эту волну (см. rules.md §5, последний пункт). Если
   попросил — тогда прочитай каждый нужный файл, убедись что существует, и только тогда
   прикладывай как обычно; при сбое — правило 6.

## Шаг 3. Получить номер волны и номер КП

Сначала покажи пользователю предварительный номер (не фиксируя его):
```
python3 .claude/skills/offer-drafter/scripts/kp_number.py peek <PRODUCT>
```
Это НЕ меняет состояние — можно звать сколько угодно раз.

Только после того как пользователь подтвердил волну (шаг 1) и вложения проверены (шаг 2),
зафиксируй номер:
```
python3 .claude/skills/offer-drafter/scripts/kp_number.py commit <PRODUCT>
```
Полученный `kp_number` и `wave` используются для всех писем этой волны (один номер КП на
всю волну, см. rules.md §3). Не вызывай `commit` больше одного раза на волну и не вызывай
его до подтверждения — иначе номера "сгорают" впустую.

## Шаг 4. Создание драфтов — строго по одному, в обратном порядке

Правило 7 из rules.md: бери компании из списка, подтверждённого на шаге 1, **начиная с
последней в таблице и двигаясь к первой**. Для каждой компании по очереди (не параллельно):

1. **Собери письмо** по `templates/offer_email_template.md`: персонализируй 1-2 фразы под
   `fit_reasoning`/`notes` этой компании, подставь продукт, `kp_number`, обращение
   (используй `contact_person`, если он не "не найдено", иначе нейтральное обращение).
   **Тема письма обязательно персонализирована** (название компании + понятное имя
   продукта, не только номер КП) — см. rules.md §8; две компании одной волны не могут
   получить одинаковую тему. В конец `htmlBody` вставь фиксированную подпись из
   `templates/signature_html.md` как есть. Заполни и `body` (plain text) — это обязательная
   альтернатива, не только HTML. **Без конкретных календарных дат в тексте** (rules.md §4).
   Для скорости (rules.md §9) — подготовь эти персонализированные формулировки для всех
   компаний волны заранее, одним проходом, до начала самих вызовов `create_draft`.

2. **Вложения не требуются по умолчанию** (rules.md §5, решение пользователя от
   22.10.2026) — не прикладывай файлы из manifest к `create_draft`, и не пиши в тексте
   письма ничего про "attached"/"will be shared as attachments". Если пользователь явно
   попросил вложить документы именно в эту волну — тогда прочитай каждый нужный файл,
   закодируй в base64, передай как `attachments` в `create_draft` с `filename`/`mimeType`;
   если прикрепить не получилось — правило 6 (не оставлять "грязный" драфт).

3. **Вызови `create_draft`** (`to` — email компании из buyers.xlsx; если email "не
   найдено" — пропусти эту компанию, сообщи пользователю отдельно, что по ней нужен
   email вручную, и НЕ создавай для неё драфт; переходи к следующей).

4. **Проверь результат**: убедись, что в ответе есть `id` и что вложений ровно столько,
   сколько должно быть по manifest. Если драфт создан без вложений, с неполным набором
   вложений, или вообще вызов упал с ошибкой — сначала в любом случае: если драфт всё же
   был создан (есть `id`) — удали его `delete_draft` немедленно. Дальше по правилу 6
   `rules.md`, в зависимости от режима:
   - **Автономный полный пайплайн** — зафиксируй эту компанию как пропущенную
     (`record_draft.py --status "Ошибка - пропущено (авто)"` с причиной в `--history-note`)
     и переходи к следующей компании волны; волна не останавливается.
   - **Обычный ручной запуск** — **остановись полностью**, не создавай драфты для
     оставшихся компаний волны, сообщи пользователю: на какой компании (и на какой позиции
     в таблице) случилась остановка, что именно произошло, какие компании до этого места
     уже успешно обработаны (и их позиции), а какие ещё не тронуты. Это и есть смысл
     правила 7 для этого режима — чтобы пользователь мог точно назвать диапазон
     "бракованных" писем.

5. **Если всё прошло успешно** — сразу (не откладывая на конец волны) зафиксируй это в
   таблице:
   ```
   python3 .claude/skills/offer-drafter/scripts/record_draft.py output/buyers.xlsx \
     --company "Точное название компании как в таблице" \
     --kp "<kp_number с шага 3>" --wave <wave с шага 3> \
     --status "Драфт КП создан (не отправлен)" \
     --next-step "Проверить черновик в Gmail и отправить вручную" \
     --history-note "Создан драфт КП <kp_number>, не отправлен — ожидает проверки"
   ```
   Это обновит статус/номер КП/волну на листе Buyers и добавит запись в лист
   "История контактов" — без этого шага прогресс волны не виден в таблице.

6. Переходи к следующей (по порядку обработки, т.е. предыдущей по таблице) компании.

## Шаг 5. Итоговый отчёт

После волны (успешной полностью, прерванной ошибкой в ручном режиме, или завершённой со
сквозными пропусками в автономном режиме) сообщи пользователю:
- номер волны и номер КП;
- сколько драфтов реально создано, список компаний в порядке таблицы (с номерами строк);
- **все** пропущенные компании (нет email, не прошли QC, ошибка создания драфта) —
  отдельным списком, с конкретной причиной по каждой, никогда молча;
- в ручном режиме, если была остановка по ошибке — на чём именно, какая позиция в
  таблице, что сделано (включая удаление "бракованного" драфта, если он создавался); в
  автономном режиме — что волна прошла целиком с пропуском перечисленных компаний;
- прямое напоминание: это черновики в Gmail, НЕ отправлено автоматически. Отправка —
  следующий шаг, который делает пользователь вручную, пока не будет отдельно включена
  автоматическая отправка по его явному указанию.

## Терминология

- **КП / Soft Commercial Offer** — см. глоссарий в `buyer-finder/SKILL.md`, используется
  тот же смысл.
- **Волна (wave)** — одна партия писем по одному продукту, отправляемых/черновимых за один
  проход; у волны один номер КП на всех получателей.
- **Manifest вложений** — файл `attachments/<PRODUCT>/manifest.json`, список файлов,
  заранее согласованных с пользователем для конкретного продукта.
