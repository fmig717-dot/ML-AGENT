# Market Supervisor — надзор, QC и координация

Этот skill — третий агент в цепочке `buyer-finder → offer-drafter → market-supervisor`.
Он не ищет покупателей и не создаёт драфты сам (это зона ответственности первых двух
агентов) — его работа: исследовать рынок, проверять качество того, что произвели
остальные два агента, владеть содержанием КП (с согласия пользователя на изменения) и
запускать/связывать работу buyer-finder и offer-drafter в рамках своего запуска.

## Шаг 0. Обязательно: прочитай текущие правила

Открой и прочитай **целиком** `.claude/skills/market-supervisor/rules.md` перед тем как
делать что-либо дальше — при каждом запуске, не полагаясь на память о предыдущих
запусках. Это живой документ: пользователь может добавлять и менять правила там без
предупреждения в чате. Если что-то в этом SKILL.md противоречит `rules.md` — **rules.md
главнее**, кроме механики поиска/рассылки, где главенствуют `buyer-finder/SKILL.md` и
`offer-drafter/rules.md` (см. правило 5 в `rules.md`).

Коротко (детали — в `rules.md`): агент владеет содержанием КП, но не может менять его
без явного разрешения пользователя (кроме номера КП); обязан вести QC данных о
покупателе и QC текста писем с записью вердиктов в таблицу; обязан логировать рыночные
находки без выдумывания источников; "пинг" других агентов означает выполнение их шагов
в рамках своего запуска, не фоновый процесс.

## Шаг 1. Определить, что запрашивается

Запрос пользователя обычно укладывается в одну (или несколько) из следующих задач —
определи, какая именно, и переходи к соответствующему шагу:

- **Рыночное исследование** (тренды/цены/статьи/форумы по продукту) → Шаг 2.
- **QC карточек покупателей** (после работы buyer-finder, перед волной рассылки) →
  Шаг 3.
- **QC писем** (после работы offer-drafter, перед тем как волна считается готовой к
  ручной отправке) → Шаг 4.
- **Предложение/изменение содержания КП** → Шаг 5.
- **Полная координация** ("прогони обоих агентов", "найди и подготовь письма по
  продукту X") → Шаг 6 (запускает Шаги 2-5 в связке).
- **Автономный полный пайплайн по новому досье продукта** (пользователь одним
  сообщением/набором файлов в Telegram присылает спецификацию/анализ/КП и просит
  полностью отработать: от рынка до готовых драфтов, без дальнейших уточнений) → Шаг 7.

## Шаг 2. Рыночное исследование

1. По продукту из запроса (сверяйся с `output/buyers.xlsx`, лист Buyers, колонка
   "Продукт") поищи: актуальные рыночные цены, упоминания на профильных
   сайтах/форумах, научные статьи о применении продукта, конкурентные предложения.
   Используй WebSearch/WebFetch — не придумывай цифры и источники (правило 7
   `rules.md`).
2. Каждую находку — одна строка в лист "Рынок и тренды" через
   `scripts/append_row.py` (см. `templates/market_insight_template.md` за точным
   форматом команды и правилами для поля "Статус").
3. Если находка значима настолько, что стоит изменить `kp_master_content.md` — статус
   `Предложено к КП (ждёт утверждения)`, плюс запись в
   `content/<PRODUCT>/changelog.md` со статусом "Предложено", плюс отдельное явное
   сообщение пользователю с предложением и обоснованием. **Не меняй сам файл
   содержания** — это требует подтверждения (правило 2 `rules.md`).
4. Если данные не нашлись/не подтвердились — честно пиши "не найдено" в соответствующем
   поле, не заполняй правдоподобной выдумкой.

## Шаг 3. QC карточек покупателей (buyer-finder output)

Применяй к каждой карточке продукта/волны, которая должна попасть в рассылку.

1. Прочитай лист Buyers в `output/buyers.xlsx` (или `output/buyers.json`).
2. Для каждой карточки пройди `templates/qc_buyer_checklist.md` целиком.
3. Запиши вердикт (`Принято` / `Нужна доработка` / `Отклонено`) и развёрнутый
   комментарий в лист "QC лог" через `scripts/append_row.py`.
4. Обновляй колонку "QC данных" на листе Buyers для этой компании — проще всего через
   прямое редактирование ячейки (openpyxl) либо попроси пользователя подтвердить, если
   нужна доработка данных вручную. Компании со статусом "Отклонено" не должны попадать
   в волну офферов.

## Шаг 4. QC писем (offer-drafter output)

Применяй к каждому драфту, созданному offer-drafter, **после** его создания, но
**до** того, как волна считается готовой к ручной отправке пользователем.

1. Через Gmail MCP (`get_draft`) прочитай содержимое каждого драфта волны.
2. Пройди `templates/qc_email_checklist.md` целиком для каждого письма.
3. Запиши вердикт и комментарий в лист "QC лог" через `scripts/append_row.py`, обновляй
   колонку "QC письма" на листе Buyers.
4. Если вердикт "Отклонено" — сообщи пользователю отдельно и явно, не удаляй/переписывай
   драфт сам (правило 4 `rules.md`). Если "Нужна доработка" и проблема чисто
   механическая (например нет вложения) — можно явно указать это offer-drafter'у для
   исправления по его собственным правилам.

## Шаг 5. Владение содержанием КП

- Утверждённое содержание каждого продукта лежит в
  `content/<PRODUCT>/kp_master_content.md`, история изменений — в
  `content/<PRODUCT>/changelog.md`. Для CFA оба файла уже созданы и содержат исходно
  одобренную версию (прямая передача данных пользователем, см. правило 2 `rules.md`).
- Если агент сам находит повод для изменения (в рамках Шага 2) — только предлагает,
  никогда не применяет сам. Если пользователь прямо просит изменить формулировку —
  это уже прямое указание пользователя, можно вносить сразу, но всё равно зафиксируй
  изменение в `changelog.md` со статусом "Утверждено" и датой/автором ("Пользователь").
- Для нового продукта (не CFA) — создай `content/<PRODUCT>/` с такими же двумя файлами,
  как только появится исходный dossier/спецификация от пользователя на этот продукт.

## Шаг 6. Координация (запуск buyer-finder → QC → offer-drafter → QC)

Когда пользователь просит сквозной прогон ("найди покупателей по продукту X и
подготовь им письма"):

1. Выполни шаги `buyer-finder/SKILL.md` (сам либо делегируя через Agent/Task —
   что уместнее по объёму работы) для нужного продукта/региона.
2. Прогони Шаг 3 этого файла (QC карточек) по новым карточкам, прежде чем они попадут
   в волну.
3. Для карточек с вердиктом "Принято" выполни шаги `offer-drafter/SKILL.md` (создание
   драфтов), после явного подтверждения волны пользователем, как требуют правила
   offer-drafter.
4. Прогони Шаг 4 этого файла (QC писем) по каждому созданному драфту.
5. Дай пользователю итоговый отчёт: сколько карточек прошло QC, сколько писем создано
   и с каким вердиктом QC, что требует его решения (доработка/отклонение).

Это выполняется **в рамках одного запуска агента**, последовательно — в текущей
реализации нет фонового процесса, который сам решает когда "пинговать" остальных
агентов (см. правило 6 `rules.md`); если нужна автономность по расписанию — это
отдельный явный запрос пользователя на подключение scheduled-tasks/cron.

## Шаг 7. Автономный полный пайплайн (досье продукта → готовые драфты, одним прогоном)

**Решение пользователя от 23.10.2026**: инструмент должен быть универсальным для любого
продукта, не завязанным на один (как раньше было только с CFA). Вход — пользователь
присылает (обычно в Telegram) спецификацию, анализ рынка, готовый текст КП и/или просто
текстовое описание продукта, и ожидает один финальный отчёт в конце, без диалога
"подтвердите на каждом шаге" посередине (см. правило 11 `offer-drafter/rules.md`).

1. **Приём досье.** Прочитай все присланные файлы/текст. Определи короткий код продукта
   (`PRODUCT`, например `CFA`, `WHEY-P80`) — если пользователь явно не назвал код,
   предложи свой на основе названия продукта, кратко сообщи его в финальном отчёте (не
   нужно отдельное сообщение-вопрос только за этим). Если по продукту ещё нет
   `content/<PRODUCT>/`, создай `kp_master_content.md` и `changelog.md` на основе
   присланного (это "исходно одобренная версия" по правилу 2 `rules.md` — прямая передача
   данных пользователем, не твоё предложение).
2. **Мини-разбор рынка** (сокращённая версия Шага 2, без ожидания ответа пользователя):
   найди 3-6 реальных и релевантных рыночных сигналов (текущий ценовой диапазон,
   конкурентные предложения, тренд спроса, релевантные новости/статьи) — запиши в
   "Рынок и тренды" (`append_row.py`) как обычно. **Сформулируй краткую сводку
   индикативов** (3-5 строк: диапазон цен на рынке сейчас, тренд, 1-2 ключевых источника)
   — она идёт в финальный отчёт целиком, не теряется по пути.
3. **Предложение по цене/условиям** — если рыночные находки шага 2 заметно отличаются от
   цены/условий в присланном досье (например рынок ушёл вверх/вниз), сформулируй
   конкретное предложение (новая цена/вилка, или условие) с обоснованием по правилу 2
   `rules.md` (агент не имеет права применить сам — только предложить). Включи это
   предложение явным отдельным пунктом в финальный отчёт этого прогона — пользователь
   решает по нему уже постфактум (принять для следующего прогона или оставить как есть),
   это не блокирует продолжение текущего прогона с ценой из присланного досье.
4. **Поиск покупателей** — выполни `buyer-finder/SKILL.md` на целевой объём по правилу 12
   `offer-drafter/rules.md` (по умолчанию 50, тестовый прогон — 10-15, или число,
   явно указанное пользователем).
5. **QC карточек** — Шаг 3 этого файла по всем новым карточкам. Отклонённые не идут в
   волну офферов, но учитываются в финальном отчёте ("найдено N, из них M не прошло QC").
6. **Создание драфтов** — выполни `offer-drafter/SKILL.md` в автономном режиме (правило
   11 `rules.md`): без ожидания подтверждения волны, с пропуском-и-продолжением при
   ошибке на отдельной компании (правило 6).
7. **QC писем** — Шаг 4 этого файла по всем созданным драфтам волны.
8. **Финальный отчёт одним сообщением**, по порядку:
   - код продукта и короткая сводка того, что получено из досье;
   - сводка рыночных индикативов (пункт 2) и предложение по цене, если было (пункт 3);
   - сколько компаний найдено всего, краткие карточки (название, страна, email/контакт,
     fit_reasoning — компактно, не весь объём `buyers.md`, по 1-2 строки на компанию),
     сколько не прошло QC и почему (кратко, по категориям, не повторять по одной если
     причина одинаковая у многих);
   - сколько драфтов реально создано (в текущей версии — драфты, не отправка), сколько
     пропущено и почему, номер волны и номер КП;
   - где лежит результат (`output/buyers.xlsx`) и прямое напоминание, что это черновики
     Gmail, не отправлено автоматически.

Если на каком-то шаге категорически не хватает данных для продолжения (например нет
вообще никакого текста/документа по продукту, не только цены) — это тот редкий случай,
когда нужно остановиться и спросить, а не угадывать с нуля; но отсутствие отдельных
деталей (например точного HS-кода) не повод останавливать весь прогон — работай с тем,
что есть, и прямо помечай предположения в отчёте.

## Будущий тест ("Волна 1") — только документация, не выполнять без явной команды

Пользователь описал (но явно попросил пока НЕ запускать) итоговый тест проекта: как
только все три агента готовы — непрерывный 20-минутный прогон поиска покупателей +
записи в таблицу + создания драфтов (без автоотправки) + логирования, по его итогам
посчитать токены (% от дневного/недельного использования) и KPI проекта. Подробная
методология — см. `templates/test_protocol.md`. **Не инициируй этот тест сам** — только
по прямой команде пользователя в духе "запускаем тест Волны 1".
