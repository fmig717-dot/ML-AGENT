# Протокол теста "Волна 1" — только документация, пока не выполнять

Этот файл описывает методологию будущего итогового теста проекта, который пользователь
анонсировал, но явно попросил не запускать сейчас ("Пока к разработке не приступаем, я
лишь показываю полный маршрут, финальную точку этого проекта"). Он здесь, чтобы агент
был готов выполнить тест механически правильно, когда пользователь прямо скажет
"запускаем тест".

## Что такое "Волна 1"

Все компании, которые получится найти и довести до карточки+драфта за один
непрерывный 20-минутный прогон поиска-записи-драфта-логирования, **плюс** 3 компании,
уже найденные ранее для CFA (то есть первая реальная "боевая" волна проекта — не
тестовый прогон на игрушечных данных).

Пользователь намеренно не называет минимальное число компаний, которое считается
успехом — если по его собственной оценке результата за 20 минут недостаточно, он
может прекратить дальнейшую разработку. Агент не должен пытаться угадать/подогнать под
несуществующий порог — просто честно выполнить процесс на максимальной скорости и
зафиксировать реальный результат.

## Пошаговая механика теста (когда будет дана команда на запуск)

1. Зафиксировать время старта и количество уже существующих карточек в
   `output/buyers.xlsx` (чтобы отделить "существующие 3" от "найденные за 20 минут").
2. Выполнить `buyer-finder/SKILL.md` непрерывно, одну итерацию поиска за другой, пока
   не истекут 20 минут — записывая каждую найденную карточку сразу в `buyers.xlsx`
   (не копить в памяти и записывать пачкой в конце).
3. По каждой новой карточке — QC данных (Шаг 3 `SKILL.md` market-supervisor),
   неотложно, не откладывая на после 20 минут.
4. После истечения 20 минут (поиск останавливается независимо от того, с середины
   какой компании это произошло) — прогнать `offer-drafter/SKILL.md` по всем карточкам
   волны (новым + 3 существующим) с вердиктом QC "Принято", создавая драфты в
   обратном порядке таблицы, как требуют правила offer-drafter.
5. QC писем (Шаг 4 `SKILL.md`) по каждому созданному драфту.
6. Зафиксировать в лист "Лог запусков": дата, продукт, критерии/регион поиска,
   найдено/принято/отклонено с причиной, источники.
7. Зафиксировать в лист "KPI и токены" (через `scripts/append_row.py`) минимум:
   - `Найдено карточек за 20 минут` (число)
   - `Прошло QC данных ("Принято")` (число)
   - `Создано драфтов` (число)
   - `Прошло QC писем ("Принято")` (число)
   - `Токены, потрачено на тест` (число — из метаданных запуска/отчёта среды)
   - `% от дневного лимита/использования` (посчитать относительно дневной квоты
     пользователя — узнать базу у пользователя, если неизвестна)
   - `% от недельного лимита/использования` (аналогично)

## KPI, которые нужно посчитать по итогам теста

Эти метрики — не хардкод, а то, что реально посчитано по результатам конкретного
прогона:

- **Скорость поиска**: карточек/минуту за 20-минутное окно.
- **Конверсия в качество**: доля карточек, прошедших QC данных "Принято" без доработки.
- **Конверсия в письмо**: доля принятых карточек, по которым успешно создан драфт без
  ошибок (без эмейла → не создаётся драфт, это ожидаемо и не ошибка).
- **Качество писем**: доля драфтов с вердиктом QC "Принято" без доработки.
- **Стоимость в токенах на одну готовую (принятую) пару карточка+драфт**: общие токены
  теста / число готовых пар.

## Что делать агенту, если пользователь остановит разработку по итогам теста

Если по результатам теста пользователь решает прекратить разработку — зафиксировать
финальный KPI-отчёт в "KPI и токены" как есть (честно, без попытки "подправить
постфактум"), и ничего не предлагать взамен автоматически — решение полностью за
пользователем.
